# Agentic Loom Fork: Complete Feature & Tool Report

This report serves as a comprehensive overview of the newly introduced features, tools, and structural upgrades made to the Loom repository. This fork transitions Loom from a basic inference engine into a smart, autonomous, multi-model orchestrator capable of delegating subtasks across models via native tool injection.

---

## 1. Core Features & Architectural Upgrades

### Agentic Model Chaining & Pipeline Orchestration
- **Concept:** A primary general-purpose model acts as a top-level orchestrator. If a task exceeds its capabilities (e.g., vision processing, heavy math, specific coding), the model delegates subtasks to specialized local models.
- **Implementation:** The `chain_request` tool is natively injected into the model's context. The model breaks the request into a series of `sub_tasks`, each requiring specific capabilities. The Loom backend executes these subtasks sequentially across the selected specialist models and passes the aggregated results back to the primary model for final synthesis.

### Dynamic Capability Routing
- **Concept:** The system removes reliance on hardcoded model names (like `qwen2.5-vl-7b:latest`), instead routing subtasks dynamically based on a model's stated capabilities and semantic descriptions.
- **Implementation:** The `selectModelForTask` function evaluates available models based on their metadata (name, family, system prompt, and custom descriptions). The orchestrator automatically routes tasks matching keywords (e.g., `vision`, `code`) to the most appropriate loaded model.

### Modelfile 'DESCRIPTION' Keyword & Model Awareness
- **Concept:** Models need semantic meaning so the orchestrator knows what they do.
- **Implementation:** The Modelfile parser was upgraded to natively support the `DESCRIPTION` keyword. When models interact, the backend retrieves a list of all installed models alongside their descriptions and injects this directly into the context (inside the `chain_request` tool description). The orchestrator model is thus intrinsically "aware" of the capabilities of its peers.

### Anthropic API Proxy Translation
- **Concept:** Loom translates the Anthropic (`/v1/messages`) endpoint for seamless integration with client applications like Claude Code.
- **Implementation:** The proxy was upgraded to automatically determine and route requests to a vision-capable model if an explicit model is omitted or if "claude" is specified, relying completely on dynamic routing rather than hardcoded fallbacks.

## 2. Natively Injected Tools

This fork extends Loom by automatically injecting a robust suite of system and orchestration tools into the context of capable models. The client application does not need to define or manage these tools; they are handled natively by the backend.

### Orchestration Tools

#### `chain_request`
- **Purpose:** Delegate a complex request to a chain of specialist models.
- **Parameters:**
  - `reason`: Explanation of why the model cannot handle the task alone.
  - `sub_tasks`: An ordered list of tasks to execute across specialist models, specifying descriptions, prompts, and `required_capability` (e.g., vision, code, math). Models can specify a `preferred_model` directly chosen from the injected list of available models.

### System Management Tools (`system_tool`)

The `system_tool` allows the model to perform system-level management actions. It exposes the following `action` enumerations:

- **`restart`**
  - **Purpose:** Gracefully reboot the Loom server runtime.
- **`load_model`**
  - **Purpose:** Pre-load a specific model into VRAM/Memory (requires `model_name` parameter).
- **`unload_model`**
  - **Purpose:** Evict a specific model from memory to free up resources (requires `model_name` parameter).
- **`get_status`**
  - **Purpose:** Retrieve runtime error/exception stats, warning logs, and the count of active model runners currently in memory.
- **`list_models`**
  - **Purpose:** Retrieve a list of all locally available models, their sizes, families, system prompts, and tool support abilities.

## 3. Developer & Integration Enhancements

- **Client Application Independence:** Because the orchestration and tool logic exists natively in the Go backend, client applications (Python, JS, terminal) immediately inherit multi-model orchestration without requiring extra integration logic.
- **Robust Error Handling:** Timeout limitations on backend connections (such as Python sandbox instances) were removed, preventing premature disconnects when aggressively loading large models or delegating long-running subtask chains.
